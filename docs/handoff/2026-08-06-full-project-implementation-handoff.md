## 4. 已确认的产品边界

### 4.1 产品核心

* Workspace 是长期数据、知识、记忆和扩展配置边界。
* 一个 Workspace 可以创建多个 Conversation。
* Conversation 支持多轮消息、流式进度、停止和断线恢复。
* 会话附件默认只在当前会话可见；用户明确“加入空间”后才成为跨会话可检索的空间文档。
* 图片和文件需要可见处理状态、失败原因、版本和稳定来源定位。
* 长期记忆与会话历史分离；记忆必须可查看、确认、编辑、停用、删除和追溯来源。
* 复杂研究可派出受限子代理，但必须有角色、预算、权限和取消边界。
* Python 只能在隔离沙箱运行，默认无网络，输出作为可审计研究产物。
* 回答应保存稳定 Citation；用户选中文本后可发起 Evidence Check。
* 证据核验只返回支持、反驳、证据不足或不可核验，不宣称绝对真相。
* Skill 是版本化工作方式，不是任意可执行代码。
* MCP 插件通过安装、空间启用、会话覆盖、Agent 白名单和逐次审批共同决定是否可用。
* 写入、删除、发送、发布和代码执行默认需要用户确认。

### 4.2 分期范围

严格按 PRD 的 M1、M2、M3 顺序推进：

* **M1：多轮空间与可信资料。** 空间、多个会话、持久化消息、流式恢复、图片/文件、空间文档、深度研究任务、稳定引用和空间隔离。
* **M2：记忆、核验与执行能力。** 长期记忆、Python 沙箱、受限子代理、选区证据核验、受信任 Skill 和 MCP 插件、高风险审批与调用记录。
* **M3：插件市场与协作治理。** 插件版本、审核、签名、升级回滚、第三方发布治理、成员角色、用量与组织策略。

目标是完成整个新项目，但必须先完成并验证 M1，再继续 M2、M3。不得用只有页面或 mock、没有真实业务闭环的骨架宣称项目完成；也不得因为最终范围大而跳过阶段性验证。

## 6. 实施规则

* 始终使用简体中文沟通、计划和交接。
* 先设计和计划，再开始代码；但计划确认后持续执行，不重复发散产品范围。
* 优先做小而完整的纵向闭环，保持每个阶段可运行、可验证。
* 测试必须验证真实产品行为，不验证枚举数量、字段数量、方法数量或其他代码结构。
* 附件、记忆、检索、插件和研究产物必须以 Workspace 隔离为第一约束。
* 不把文档原文或全部对话写成长期记忆；不把模型输出直接当作已确认事实。
* 不让 Skill 直接获得任意代码执行；不信任 MCP Server 自报的安全注解。
* 不把插件密钥、用户凭证或宿主环境变量暴露给模型、沙箱或不相关插件。
* 不展示或持久化模型隐式思维链；只保存任务状态、工具调用、证据和面向用户的结果。
* 遇到外部依赖或网络受限时，区分 mock/本地测试证据与真实集成证据。
* 只在子任务独立且不会写冲突时使用 MultiAgent；使用长等待，不随意中断子代理。
* 保护所有现有用户文件和兄弟仓库；不做破坏性移动、删除、reset 或清理。
* 除非用户明确要求，不创建 commit、不 push、不修改远程仓库。

## 7. 完成定义

只有同时满足以下条件，才可以声称相应里程碑完成：

1. 对应 PRD Must 需求形成真实用户闭环。
2. 对应全局验收场景通过自动化测试或可复现的集成验证。
3. 前端可操作，后端状态真实持久化；刷新后核心数据不丢失。
4. 流式、取消、重试和错误状态不是静态演示。
5. 空间隔离、高风险审批、沙箱和插件权限有负向测试。
6. 测试报告包含实际命令与通过/失败/跳过统计，而不是只写“构建成功”。
7. 文档说明启动、配置、测试、数据清理、备份和已知限制。
8. 没有用 mock 替代必须交付的生产路径；若某外部系统只能 mock，明确列为未完成集成。
